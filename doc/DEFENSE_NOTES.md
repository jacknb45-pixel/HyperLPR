> 对应 6 分钟框架中「选定应用 + 源码模块结构」环节（约 1.5 分钟）。
> 原则：**开题里程碑只交「选了什么应用、源码长什么样」**，不讲性能测试——
> 真机基线已提前跑完，但只在被追问时作为"进度佐证"抛出，不占主讲述时间。

## 一、90 秒讲稿骨架

1. **应用是什么（20 秒）**：HyperLPR，开源中文车牌识别框架，推理流水线是固定的四阶段——
   定位 → 对齐 → 识别 → 分类。选它的理由是四条边界清晰：纯 CPU 可跑、有官方移动端部署、
   模块天然分段、开源可改（我就是改它源码做解耦的）。
2. **源码模块结构（40 秒）**：原库 1697 行分五层（接口 / 推理算子 / 通用工具 / 类型定义 / 配置），
   对外只暴露一个写死的 `run()`——**这是"不能划分"的根因**。
   我的 Part A 工作：把这条硬编码链拆成四个可独立调度的算子，让调用方能自由决定
   "哪个算子在端、哪个在云"。*其中只有对齐是纯几何运算，其余三个是 AI 推理。*
3. **切分点候选（30 秒）**：数据流上有一个"张量体积的悬崖"——对齐之后，载荷从 MB 级原图
   掉到 KB 级切片（真机实测 5.81~12.73 KB，对 2 MB 级原图削减 160 倍）。
   而识别阶段的输入恰恰只是这张切片，卸载它既不增加流量、又省掉最贵的一块算力；
   反之若卸载检测，必须上传整张原图。**所以"对齐之后"是候选切分点。**
   这个位置由算法结构决定（角点由检测头白送、对齐产出规整小图），不随硬件变化。

## 二、被追问时才用的数字（真机实测）

| 数字 | 含义 |
|---|---|
| **150.52 ms / 84.2 MB** | Android 真机 1080p 单次识别端到端时延 / 进程内存 |
| **141.49 ms** | 四算子逐阶段合计（det 68.00 / align 0.88 / rec 70.08 / cls 2.53） |
| **5.81~12.73 KB** | 对齐后切片载荷，对 385 KB 图削减 66×，对 2 MB 级原图削减 160× |

口径要点：以上全部是**在 Android 真机 C++ 层对四个算子直接打点**得到的，不是用"整体减子集"的差分推算。

## 三、预期提问与回答口径

**Q1 "为什么开题报告里没有性能测试章节？"**
→ 按课程里程碑，M1 交付的是「选定应用 + 源码模块结构」；各划分方式的性能对比属于中期（11/29）。
报告里的实测数字只用于支撑"切分点在哪"，不构成性能评估章节。

**Q2 "为什么选车牌识别，随便换个应用不行吗？"**
→ 需要同时满足四个条件：计算密集（有卸载动机）、阶段间数据体积不连续（有切分点）、
纯 CPU 可跑（端云可等价复现、变量可控）、开源可改（Part A 要动源码）。多数 demo 级应用缺第二或第三条。

**Q3 "对齐不是 AI，为什么不把它放到云端？"**
→ 实测：不做透视矫正直接上传裁剪区，识别一致性崩到 3/7（做对齐为 7/7）。
对齐只花 0.88 ms，买的是云端识别的**正确性**。

**Q4 "任务书说缩减超 100 倍，你们只有 66 倍？"**
→ 100 倍是任务书对 MB 级原图的估计值。实测按输入体积分档：2 MB 级相册照片 160×，
已压缩的 385 KB 图 66×。切片本身已是精度无损下限（JPEG 质量降到 q85 困难样本就开始识别错误）。

**Q5 "数据是怎么测的？在 PC 上模拟的不算数吧？"**
→ 全部在 Android 真机上测：APK 内置测试图、打开即测，不依赖 USB 调试。
逐阶段耗时是自写的 `libstage_bench.so` 链接官方 `libhyperlpr3.so` 的引擎符号，
在 C++ 层用 `steady_clock` 对每个算子前后打点，3 次 warmup + 20 轮取均值，逐阶段标准差 < 2%。
（该测量 App 与 native 库属移动端改造，按开题范围已剥离出本分支，源码归档在 `archive/stage-bench-v5`。）

**Q6 "划分方案和动态决策什么时候给？"**
→ 静态划分的多方式对比在中期（11/29，含真实云端联调）；动态自适应决策（Part C）在终期（12/21）。
开题阶段按课程要求只确定应用与模块结构。
